Snag · research notes · 2026-09-28

We tried to replace a frontier model with a 421M-parameter one. Here is what the evidence says.

Snag reviews a pull request against the issue it claims to fix and says, requirement by requirement, what was done, what is missing and what contradicts the request. We wanted its judgement engine to run locally, cheaply and privately, so we fine-tuned Laya, an open typed-decision model built on ModernBERT-large. After several training runs, a mechanics diagnostic and a controlled experiment, the small model still could not tell implemented code from missing code on repositories it had never seen. This is the full account: the architecture, every attempt, the bug in our labels that shaped all of it, and a measured comparison with simply calling a frontier model.

The problem

Coding agents now open pull requests from issues. A human reviewer then has to answer a question that ordinary review tools skip: did this change do what the issue asked, and nothing it did not? Style bots and bug finders read the diff. Snag reads the diff against the request.

The answer has to be specific to be useful. "Requirement 3, the export filename should include the report date, is missing" helps a reviewer. "The PR looks incomplete" does not. So Snag works at the level of individual requirements, each tied to an exact quote from the issue, and every verdict points at lines of code.

The architecture

Snag splits the work so that a model answers only small, well-defined questions, and plain code makes the decisions.

  1. Blind extraction. A language model reads only the issue, never the PR, and lists atomic requirements. Each must quote the issue verbatim, which code checks.
  2. Change units. Tree-sitter splits the diff into units, one per function or test, with comments stripped so code comments cannot argue with the reviewer.
  3. Typed questions. For each requirement, an engine answers narrow questions with a probability per option: how much of the requirement the candidate units implement (None, Touched, Most, Full), whether any change conflicts with it, which unit is the evidence, whether the tests assert the stated behaviour.
  4. Verdict rules. Deterministic code turns probabilities into statuses (done, partial, missing, contradicted) with thresholds, then into findings with a priority and a route.

This design matters for the rest of the story. Because the engine only answers typed questions, any engine that speaks the protocol can plug in: TypeSafe's Jev, which Snag was designed around; a generative LLM prompted to return per-option probabilities; or a small classifier like Laya. We built all three behind one interface (JevProvider), and a local server (scripts/laya/server.py) that speaks Jev's /v1/systemone protocol so Snag cannot tell the difference.

Why try a small local model at all

The obvious alternative is to send each question, or the whole review, to a frontier model such as Claude or GPT. We did build that path, and it works far better today (numbers below). We still spent the effort on a local model because a reviewer that runs on every push has constraints a chat assistant does not.

One row stopped being theoretical during the project. The engine Snag was designed around, TypeSafe's Jev, paused new signups, so we could not get a key. Vendor risk is not an abstraction when your core component depends on it. A model you own cannot be taken away.

So the bet was reasonable: if a 421M-parameter encoder could answer Snag's narrow questions well, the product would be cheaper, faster, private and more controllable. The rest of this piece is about testing that bet properly.

The training setup

The base model. Laya (convaiinnovations/laya, Apache-2.0) is a ModernBERT-large encoder with a two-layer head that scores answer options at [MASK] marker positions. It answers exactly the three question types Snag uses. We started from its typed-decisions checkpoint, 421,293,830 parameters, 843 MB in fp16.

The data. Snag has a mutation corpus: 12 small seed repositories in TypeScript, Python and Rust, each a correct PR for an issue, from which operators derive defective variants (drop a requirement, flip a condition, remove one case, unwire a call, weaken a test, and so on). We split by repository before any augmentation: 7 seeds for training, 2 for validation, 3 frozen for a final test that no experiment touched.

OracleJev. The key trick for getting training data that matches production exactly: run Snag's real pipeline on every training item, but answer its questions from the item's labels. An oracle engine records each (state, question, answer) the pipeline asks, but only when the labels decide the answer. The recorded states are therefore byte-for-byte what Snag would send the model in production.

The recipe. We trained the top 6 of 28 encoder layers plus the head with AdamW (encoder 2e-5, head 1e-4), gradient checkpointing and bf16 on an Apple M5 GPU with 24 GB of unified memory. Three unglamorous engineering fixes were needed before anything ran: padding tensor shapes to buckets so the MPS graph cache stopped exhausting memory, checkpointing only the trainable layers, and a strict server that rejects over-long inputs instead of truncating them silently, so Snag never judges code the model did not see.

Six attempts, in order

1. v1: high accuracy, useless reviews

The first fine-tune looked like a success. On held-out seeds, accuracy across all typed questions rose from 43.6% to 82.1%. Then we ran it end to end inside Snag. On the held-out mutation PRs it caught 1 of 21 planted defects. It said "missing requirement, done" 31 times and "contradicted requirement, done" 19 times. The model had learned the majority answers: most training examples were "Full coverage" and "no conflict", so predicting those scored well per question and failed at the only thing that mattered.

2. v2: fixing the imbalance, and finding shortcuts

We added counterfactual "missing" twins (the same requirement with its implementing code removed) and balanced the classes. An audit before the run finished found two shortcuts in our own augmentation: distractor units carried IDs like D1 while real units were U1, and twins had exactly one fewer candidate than their originals. Either reveals the answer without reading code. With the loss flat as well, we stopped the run at step 90 of 394 and fixed both. A later probe showed the twins still leaked through language mixing, so we rebuilt them from same-repository decoys. A shallow-feature probe that once beat the majority baseline by up to +0.30 fell to about +0.08.

3. The mechanics diagnostic: the trainer works

When a later memorisation check failed, it was tempting to blame the trainer. We tested that directly with 27 hand-written, unambiguous examples in matched pairs, instrumented gradient flow, optimiser membership, marker positions and option order. The model fit all 27 by step 40 (26 with checkpointing or shape bucketing on), the 5 matched contradiction pairs flipped the right way (for a 404-versus-400 status-code bug, P(conflict) was 0.017 on the correct code and 0.641 on the wrong one), and decisions were identical after save and reload. The machinery was sound. The problem was elsewhere.

4. Stage A: still nothing on held-out cases

On the cleaned data, training only the four core questions, the model still found 0 of 43 missing requirements on held-out seeds and said "conflict" on 92% of cases that had none. Loss fell. Discrimination did not appear.

5. The label audit: the actual root cause

This is the part worth reading twice, so it gets its own section.

6. E7: a controlled experiment on clean pairs

With corrected labels we built the cleanest test we could: 27 matched pairs, each the same requirement shown once with its implementing code and once with that code removed, taken straight from the corpus with no synthetic augmentation. We used 3-fold cross-validation grouped by repository, so every pair was judged by a model that had never seen its codebase, with a fixed training budget and no checkpoint picked on validation results.

The model memorised its training codebases and learned nothing that transferred. Fine-tuning moved it from "always implemented" to guessing; pair ranking stayed at a coin flip. With 32 to 44 training examples per fold, more data could change this, but there was no improvement signal to justify scaling, so fine-tuning is paused.

The labels were wrong

Every mutation item came with a label derived from its operator's name. Drop a requirement's code, and the label says "missing". Remove one case, and it says "partial". That seemed safe. It was not.

We wrote a status rubric (docs/status-rubric.md) that judges from the code alone: a requirement is missing only if nothing handles the situation it names, and contradicted if code handles that situation with an outcome the requirement rules out. Then we re-judged every targeted label across the 9 development seeds.

36 of 83 targeted labels, 43%, were wrong. The pattern is consistent. Remove exponential backoff from a retry loop and the code falls back to a fixed delay: that is not a missing requirement, it contradicts "delays double each time". Remove the case that parses "2" as a version and it now returns an error: contradicted, not partial. A helper that is never called is never "partial"; it is missing, or the call site now does something else.

Every earlier training run learned from these labels. That alone is a plausible explanation for the failures, independent of model capacity. It also taught us something about evaluation: our first comparisons of Snag's engines scored them against the same wrong labels, which made one engine look better than another when, under the rubric, it was not.

Against frontier models

On the 7 items where we could afford to run B, B surfaced 5 of 6 target defects with the right type and A 4 of 6; both got 5 of 7 reviews entirely right. With the original labels the order was reversed. On 7 items that is a tie, not a ranking.

The frontier model is far ahead of the small one, and still not good enough. On 30 real merged patches from SWE-bench Verified, where there is no planted defect, we adjudicated every finding the best frontier configuration raised. Only 2 of 9 decidable findings held up. The largest source of false findings was code on the fix path flagged as unexplained (5 of the 7 that remained after our last two fixes); before those fixes, requirements invented from things the issue never asked for were the other big one. A frontier model removes the capacity problem. It does not remove the need for clean task definitions, correct labels and careful scoping.

Build or buy: the verdict

For this product, today, the evidence points one way.

  1. Use a frontier model as the engine now. It is the only option that reasons about code well enough to be worth improving, it needs no training data, and on mutation PRs a single call per PR cost $0.043 against $0.158 for our structured pipeline, with no measurable loss on the 7 items we could compare.
  2. Keep the typed-question interface. It is what let us swap engines, run a strict evaluator and hold every engine to the same rubric. It is also the path back to a local model.
  3. Do not expect a small model to learn this task from a few synthetic repositories. Our data was 9 development seeds written in one style; that is far from the diversity code review needs.
  4. Revisit local only with a specific reason. Many more independent codebases, human-checked labels, or verified frontier answers to distil from. A small model makes sense later as a pre-filter that routes obvious cases away from the paid model, if its routing errors are measured and acceptable.

The arguments for a local model were never wrong. Cost, latency, privacy and control still matter, and they will matter more as usage grows. They are reasons to keep the door open, not reasons to ship a model that cannot yet do the job.

What we would tell ourselves

  • Audit labels before training anything. Nearly half our "missing" and "partial" labels were wrong, and no recipe fixes that.
  • Question-level accuracy can hide total failure. 82% per question coexisted with catching 1 of 21 real defects.
  • Memorising is not learning. The mechanics set fit 27 of 27, training pairs fit 38 of 42, and unseen pairs sat at chance. Only held-out, repository-grouped evaluation told the truth.
  • Augmentation leaks in ways you do not predict. IDs, candidate counts and cross-language filler all gave away the answer until we probed for them.
  • Build the strict evaluator first. Our lenient first scorer credited defects by status even when no finding reached the user, and a report bug silently dropped a system's best items. Both inflated numbers we then had to take back.
  • Report negative results with their denominators. They are the most useful thing this project produced.

What is next

The next work is data, not models: relabel the corpus from code by running each requirement's example inputs against the head code, add many more independent repositories (including human-labelled PR-issue alignment data such as PAIChecker's), and have a human check a sample of every label source. With that in place, the frontier engine gets its false findings fixed one experiment at a time, and E7 gets rerun with a specific hypothesis.

This work has clear limits. The corpus is small and synthetic, annotated by an AI model rather than people. The real-patch sample is 30 PRs. Local inference latency and cost were not measured end to end. And the target Snag is held to, at least 99% on every correctness metric within a declared scope, is not met by any engine yet. We would rather say that plainly than dress up a partial result.

Help us improve it

Snag is held to a hard bar: within a declared scope, the lower bound of the 95% interval must be at least 99% on every correctness metric, with the reviewer saying "needs human review" instead of guessing when the evidence is not decisive. No engine meets that yet. Here is how far each one is.
