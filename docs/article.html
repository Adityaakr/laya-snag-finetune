Snag · Laya · What we learned

What we learned fine-tuning a small decision model to review pull requests

Snag needs a model that makes decisions, not one that writes text. So instead of wrapping Claude or GPT, we fine-tuned Laya, a 421M-parameter decision model that answers in a third of a second on a laptop. These are our notes: the architecture, why we chose this path, what worked, what did not, and what we would do differently.

Snag reviews a pull request against the issue it claims to fix and says, requirement by requirement, what was done, what is missing and what contradicts the request. Its core is a judgement engine that answers narrow, typed questions about code. We are sharing everything we learned trying to make that engine a small fine-tuned model: the reasons, the six attempts, the label bug that shaped all of it, the honest numbers against a frontier model, and where we would like help. The results are not where we want them yet. The lessons are the useful part.

01

The problem

Coding agents now open pull requests from issues. A human reviewer then has to answer a question that ordinary review tools skip: did this change do what the issue asked, and nothing it did not? Style bots and bug finders read the diff. Snag reads the diff against the request.

The answer has to be specific to be useful. "Requirement 3, the export filename should include the report date, is missing" helps a reviewer. "The PR looks incomplete" does not. So Snag works at the level of individual requirements, each tied to an exact quote from the issue, and every verdict points at lines of code.

02

The architecture

Snag splits the work so that a model answers only small, well-defined questions, and plain code makes the decisions.

  1. Blind extraction. A language model reads only the issue, never the PR, and lists atomic requirements. Each must quote the issue verbatim, which code checks.
  2. Change units. Tree-sitter splits the diff into units, one per function or test, with comments stripped so code comments cannot argue with the reviewer.
  3. Typed questions. For each requirement, an engine answers narrow questions with a probability per option: how much of the requirement the candidate units implement (None, Touched, Most, Full), whether any change conflicts with it, which unit is the evidence, whether the tests assert the stated behaviour.
  4. Verdict rules. Deterministic code turns probabilities into statuses (done, partial, missing, contradicted) with thresholds, then into findings with a priority and a route.

The review pipeline. The engine is the part this work tried to make local.

This design matters for the rest of the story. Because the engine only answers typed questions, any engine that speaks the protocol can plug in: TypeSafe's Jev, which Snag was designed around; a generative LLM prompted to return per-option probabilities; or a small classifier like Laya. We built all three behind one interface (JevProvider), plus a local server that speaks Jev's /v1/systemone protocol, so Snag cannot tell the difference.

03

Why a decision model, not a full LLM

The obvious way to build this is to send the issue and the diff to Claude or GPT and ask for a review. We built that too, and we use it as our reference. But look at what Snag's engine actually has to do: answer "how much of this requirement do these changes implement: None, Touched, Most or Full?" and "does any change conflict with it: yes or no?", a few times per requirement, on every push. That is a decision over a fixed set of options. It is not a writing task, and a general-purpose generator is a heavy, slow and loosely fitting tool for it.

Laya is built for exactly this shape. It is an encoder that reads the question and the code once and scores every option at marked positions. It never generates a token. That one design difference is where most of its advantages come from.

  1. It is fast. On an Apple M5 laptop GPU, our fine-tuned checkpoint answered real Snag questions (about 1,100 tokens of code and context each) in 340 ms at the median and 550 ms at p95. A whole frontier review took 17.2 s at the median and 47.5 s at p95. A typical PR in our set has about 4 requirements with a few questions each, so even answered one at a time on a laptop the decisions take a few seconds, with no network round trip, queue or rate limit. On datacenter GPUs, Laya's authors report tens of milliseconds per decision.
  2. The answer is always valid. The output is a probability over the allowed options, so there is nothing to parse and nothing to truncate. Our frontier reviewer returned a truncated, unusable answer on 10 of 29 first attempts and needed retries. The decision model completed 29 of 29 reviews on the first try.
  3. Every option gets a probability in one pass. "Most: 0.62, Full: 0.31" is exactly what a verdict rule needs to set thresholds, and to abstain with "needs human review" when no option is decisive. A generative model can be asked to report probabilities, but they are text it wrote, not scores it computed.
  4. It is deterministic and pinned. The same input gives the same answer, and we verified identical decisions after saving and reloading a checkpoint. A pinned checkpoint does not change underneath you the way a hosted model version can, so calibration and evaluation stay valid.
  5. It learns your definition of done. A frontier model follows your prompt; a fine-tuned decision model can be trained on your own rubric, your own labels and your own codebases. That is the only way to push one narrow judgement towards 99%.
  6. Cost does not grow with every push. A frontier review cost us $0.017 to $0.043 for a single call and $0.158 through the structured pipeline. A reviewer that runs on every push of every PR multiplies that indefinitely. A local model costs hardware time, which is fixed and already on the desk.
  7. It is small enough to run anywhere. 843 MB in fp16. It runs on a laptop or inside a customer's own cluster, so the diff never goes to a third party for judgement. (Requirement extraction from the issue still uses an LLM today, unless that step also runs locally.)
  8. It sees exactly what it judges. Our server enforces a strict 4,096-token window and rejects anything longer instead of silently truncating, so Snag never passes judgement on code the model did not read.
  9. No vendor can take it away. The engine Snag was designed around, TypeSafe's Jev, paused new signups during this project, so we could not get a key. A model you own cannot be withdrawn, repriced or rate-limited.

The last row is the one that matters most, and it is the one this project is really about. A decision model is the right shape for the job. Whether a 421M-parameter one can learn to read code it has never seen as well as a frontier model does is an empirical question. Here is how we tested it.

04

The training setup

The base model. Laya (convaiinnovations/laya, Apache-2.0) is a ModernBERT-large encoder with a two-layer head that scores answer options at marker positions. It answers exactly the three question types Snag uses. We started from its typed-decisions checkpoint: 421,293,830 parameters, 843 MB in fp16.

The data. Snag has a mutation corpus: 12 small seed repositories in TypeScript, Python and Rust, each a correct PR for an issue, from which operators derive defective variants (drop a requirement, flip a condition, remove one case, unwire a call, weaken a test). We split by repository before any augmentation: 7 seeds for training, 2 for validation, 3 frozen for a final test that no experiment touched.

OracleJev. The key trick for training data that matches production exactly: run Snag's real pipeline on every training item, but answer its questions from the item's labels. The oracle records each state, question and answer, but only when the labels decide the answer. The recorded inputs are byte-for-byte what Snag sends the model in production.

The training and evaluation loop. The audit step came late, once it was clear the labels could not be trusted.

The recipe. We trained the top 6 of 28 encoder layers plus the head with AdamW (encoder 2e-5, head 1e-4), gradient checkpointing and bf16 on an Apple M5 GPU with 24 GB of unified memory. Three unglamorous fixes came first: bucketing tensor shapes so the MPS graph cache stopped exhausting memory, checkpointing only the trainable layers, and a strict server that rejects over-long inputs instead of truncating them, so Snag never judges code the model did not see.

05

Six attempts, in order

1. v1: high accuracy, useless reviews

The first fine-tune looked like a success. On held-out seeds, accuracy across all typed questions rose from 43.6% to 82.1%. Then we ran it end to end inside Snag. On the held-out mutation PRs it caught 1 of 21 planted defects. It turned a missing requirement into "done" 31 times and a contradicted one into "done" 19 times. Most training examples were "Full coverage" and "no conflict", so predicting those scored well per question and failed at the only thing that mattered.

2. v2: fixing the imbalance, and finding shortcuts

We added counterfactual "missing" twins (the same requirement with its implementing code removed) and balanced the classes. An audit before the run finished found two shortcuts in our own augmentation: distractor units carried IDs like D1 while real ones were U1, and twins had exactly one fewer candidate than their originals. Either reveals the answer without reading code. With the loss flat as well, we stopped at step 90 of 394 and fixed both. A later probe showed twins still leaked through language mixing, so we rebuilt them. A shallow-feature probe that once beat the majority baseline by up to +0.30 fell to about +0.08.

3. The mechanics diagnostic: the trainer works

When a memorisation check failed, it was tempting to blame the trainer. We tested that directly with 27 hand-written, unambiguous examples, and instrumented gradient flow, optimiser membership, marker positions and option order. The model fit all 27 by step 40 (26 with checkpointing or bucketing on). The 5 matched contradiction pairs flipped the right way: for a 404-versus-400 status-code bug, P(conflict) was 0.017 on the correct code and 0.641 on the wrong one. Decisions were identical after save and reload. The machinery was sound; the problem was elsewhere.

4. Stage A: still nothing on held-out cases

On cleaned data, training only the four core questions, the model still found 0 of 43 missing requirements on held-out seeds and said "conflict" on 92% of cases that had none. Loss fell. Discrimination did not appear.

5. The label audit: the actual root cause

This one gets its own section.

6. E7: a controlled experiment on clean pairs

With corrected labels we built the cleanest test we could: 27 matched pairs, each the same requirement shown once with its implementing code and once without it, taken straight from the corpus with no synthetic augmentation. Three-fold cross-validation grouped by repository meant every pair was judged by a model that had never seen its codebase, with a fixed budget and no checkpoint picked on validation results.

The model memorised its training codebases and learned nothing that transferred. Fine-tuning moved it from "always implemented" to guessing; pair ranking stayed at a coin flip. With 32 to 44 training examples per fold more data could change this, but there was no improvement signal to justify scaling, so fine-tuning is paused.

06

What the labels taught us

Every mutation item came with a label derived from its operator's name. Drop a requirement's code and the label says "missing". Remove one case and it says "partial". That seemed safe. It was not.

We wrote a status rubric that judges from the code alone: a requirement is missing only if nothing handles the situation it names, and contradicted if code handles that situation with an outcome the requirement rules out. Then we re-judged every targeted label across the 9 development seeds.

36 of 83 targeted labels, 43%, were wrong. The pattern is consistent. Remove exponential backoff from a retry loop and the code falls back to a fixed delay: that is not a missing requirement, it contradicts "delays double each time". Remove the case that parses "2" as a version and it now returns an error: contradicted, not partial. A helper that is never called is never "partial"; it is missing, or the call site now does something else.

Every earlier training run learned from these labels. That alone plausibly explains the failures, independent of model capacity. It also changed how we evaluate: our first engine comparisons scored against the same wrong labels, which made one engine look better than another when, under the rubric, it was not.

Where it stands against a frontier model

On the 7 items where we could afford to run B, B surfaced 5 of 6 target defects with the right type and A 4 of 6; both got 5 of 7 reviews entirely right. With the original labels the order was reversed. On 7 items that is a tie, not a ranking.

The frontier model is far ahead of the small one, and still not good enough. On 30 real merged patches from SWE-bench Verified, where there is no planted defect, we adjudicated every finding the best frontier configuration raised. Only 2 of 9 decidable findings held up. The largest source of false findings was code on the fix path flagged as unexplained (5 of the 7 that remained after our last two fixes); before those fixes, requirements invented from things the issue never asked for were the other big one. A frontier model removes the capacity problem. It does not remove the need for clean task definitions, correct labels and careful scoping.

So today the frontier model reads unfamiliar code far better, and the decision model has every structural advantage that a reviewer running on every push needs. We do not see them as rivals. The frontier model is our reference and our teacher: its verified answers are exactly the kind of training data the decision model was missing. The decision model is the engine we want to ship, once it earns it on data it has never seen.

08

Our learnings

If you are about to fine-tune a small model for a judgement task, these are the things we wish we had known on day one.

  • Audit labels before training anything. Nearly half our "missing" and "partial" labels were wrong, and no recipe fixes that.
  • Question-level accuracy can hide total failure. 82% per question coexisted with catching 1 of 21 real defects.
  • Memorising is not learning. The mechanics set fit 27 of 27, training pairs fit 38 of 42, and unseen pairs sat at chance. Only held-out, repository-grouped evaluation told the truth.
  • Augmentation leaks in ways you do not predict. IDs, candidate counts and cross-language filler all gave away the answer until we probed for them.
  • Build the strict evaluator first. Our lenient first scorer credited defects by status even when no finding reached the user, and a report bug silently dropped a system's best items. Both inflated numbers we then had to take back.
  • Pick the model by the shape of the output. A choice between fixed options wants a decision model. That part of our bet held up: fast, valid, deterministic answers. What failed was the data, not the shape.
  • Use the frontier model as a teacher, not only as a competitor. Its verified answers on many real codebases are the most direct way to give a small model the variety it lacked.
  • Report negative results with their denominators. They are the most useful thing this project produced, which is why we are sharing them.
09

Help us improve it

Snag is held to a hard bar: within a declared scope, the lower bound of the 95% interval must be at least 99% on every correctness metric, with the reviewer saying "needs human review" instead of guessing when the evidence is not decisive. No engine meets that yet. Here is how far each one is.

Strict scorer, rubric labels. Mutation numbers are from 2 held-out codebases; real patches are 30 SWE-bench Verified PRs.

The gap is mostly data, not models. A 99% claim needs roughly 380 error-free independent cases per metric, realistically 600 or more, and we have 2 held-out codebases and 30 real patches. These are the contributions that would move the numbers most, in order of impact.

Everything is open. The fine-tuning code, data, logs, label audit and every experiment are in laya-snag-finetune; the reviewer itself is Snag. The one rule for contributions is the one we hold ourselves to: every claim comes with its denominator, and a result counts only on data the change was not tuned on.

A small model is not the goal. A reviewer you can trust is.
